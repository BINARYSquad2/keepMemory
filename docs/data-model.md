# Модель данных и хранение

## PostgreSQL

Backend при старте подключается к уже созданной базе через `DATABASE_URL`, проверяет соединение и выполняет `CREATE TABLE IF NOT EXISTS`. Саму базу данных он не создаёт. Схема задаётся SQL в `backend/db.go`; отдельной системы миграций в проекте нет.

### `users`

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | UUID аккаунта |
| `name` | `TEXT NOT NULL` | Отображаемое имя; в JSON называется `displayName` |
| `handle` | `TEXT NOT NULL DEFAULT ''` | Никнейм |
| `bio` | `TEXT NOT NULL DEFAULT ''` | Интересы и предпочтения |
| `email` | `TEXT UNIQUE NOT NULL` | Email в нижнем регистре |
| `password_hash` | `TEXT NOT NULL` | Хеш bcrypt; не отдаётся API |
| `created_at` | `TIMESTAMPTZ` | Дата создания |

### `days`

| Колонка | Тип | Назначение |
| --- | --- | --- |
| `id` | `TEXT PRIMARY KEY` | UUID записи |
| `user_id` | `TEXT REFERENCES users(id) ON DELETE CASCADE` | Владелец записи |
| `date` | `TEXT` | Дата `YYYY-MM-DD` |
| `folder_title` | `TEXT` | Название страницы/папки |
| `text` | `TEXT` | Текст дня |
| `photo_uri` | `TEXT` | Основной кадр (обложка) |
| `photo_uris` | `JSONB` | Массив путей кадров; старые записи совместимы через `photo_uri` |
| `track` | `JSONB` | Данные выбранного трека |
| `style` | `JSONB` | Палитра и параметры оформления |
| `created_at` | `TIMESTAMPTZ` | Время создания; индексируется вместе с `user_id` |

`mood` возвращается в API как производное поле из `style.mood`; отдельной колонки для него нет. `user_id` скрыт в JSON-ответе.

## Файлы фотографий

- Файлы хранятся вне PostgreSQL в `UPLOADS_DIR/<user-id>/`; по умолчанию `UPLOADS_DIR=uploads`. Имена генерируются UUID, а принимаются только проверенные JPEG, PNG, WebP и HEIC до 15 MiB каждый.
- Новые строки `days.photo_uri`/`photo_uris` содержат внутренний путь `/api/media/<user-id>/<uuid>.<ext>`. API-ответы заменяют локальные пути 24-часовыми HMAC-подписанными ссылками. Сервер проверяет подпись, совпадение владельца и наличие ссылки на файл в записи; `/uploads` больше не раздаётся статически.
- Старые пути `/uploads/<uuid>.<ext>` остаются читаемыми через защищённый маршрут, чтобы не менять существующие строки и не требовать миграции. Загрузки, созданные после обновления, изолированы в каталогах пользователей.
- Каталог всё ещё является файловым хранилищем, а не PostgreSQL/S3. Для Railway подключите постоянный Volume к `/data` и задайте `UPLOADS_DIR=/data/uploads`; без Volume файлы могут потеряться при пересоздании контейнера. Схема БД не меняется.
- `DELETE /api/days/{id}` удаляет запись и неиспользуемые локальные фото. `GET /api/backup` отдаёт пользовательский ZIP с manifest и доступными фото (до 5000 записей/100 MiB). Это ручной экспорт, не замена автоматическим резервным копиям БД и тома.

## Ограничения альбома

Мобильный клиент допускает альбом до шести кадров. Сервер отклоняет альбом сверх лимита, ограничивает каждый файл 15 MiB и всё тело запроса 95 MiB. При ответе `413` клиент повторяет отправку только с обложкой и сохраняет дополнительные URI локально на устройстве; в таком случае дополнительные фото не синхронизируются на другие устройства.

## Пользовательские данные и внешние сервисы

- Пароли хранятся как bcrypt-хеши, JWT-секрет задаётся через `JWT_SECRET`.
- Клиент хранит JWT в SecureStore на нативных платформах и в `localStorage` в браузере.
- Поиск треков отправляет введённый запрос в iTunes Search API.
- Gemini вызывается только при настроенном `GEMINI_API_KEY` и явном включении пользователем «Разрешить Gemini» для конкретной записи. Передаются текст, имя и bio, заголовки последних пяти дней и данные трека. Фото не отправляются; цвета вычисляются локально на сервере. Без согласия используется локальный рецепт.
- На экране деталей доступен системный шаринг PNG-карточки на iOS/Android. Это отдельный визуальный экспорт; ZIP-резервная копия данных доступна через `GET /api/backup`.

Ссылки на фото остаются временными секретами: передавайте их только нужным клиентам и не записывайте query-параметры подписей в аналитические логи. На Railway отдельно включите резервное копирование PostgreSQL и тома.
